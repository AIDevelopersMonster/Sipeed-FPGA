# Семь демонстраций LiteX BIOS / ROM Explorer

[← Справочник](README.md) · [Запуск HTML](ROM_EXPLORER_GUIDE_RU.md) · [Команды реального BIOS](COMMANDS_RU.md)

Эти эксперименты можно показать посетителям: для каждой демонстрации указываются **действие**, **наблюдение** и **предел вывода**. HTML — не подключённая FPGA, а автономный интерпретатор ROM; реальный UART-лог приведён отдельно.

## DEMO 1 — Как RISC-V начинает исполнять BIOS

**HTML → 01 Исследователь → Сброс → Шаг**. Стартовый `PC=0x00000000`; первая инструкция передаёт управление к инициализации около `0x000000B0` (Reset vector → BIOS start). Следим за `PC` и записью регистров. **Показывает путь исполнения модели**, а не длительность аппаратного сброса.

## DEMO 2 — Где живёт обработчик исключений

**HTML → контрольная точка Exception vector / карта ROM → `0x00000020`**. В ROM есть код trap/exception handler и установка `mtvec` на `0x20` около `0xC0`. Сопоставляем архитектурный CSR `mtvec (0x305)` и исполняемые машинные слова. **Факт наличия кода не доказывает входа в обработчик на реальном стенде** — это цель будущей отдельной LAB-20.7.

## DEMO 3 — Почему 128 КиБ ROM «содержат» только 32 КиБ

**HTML → 03 Карта ROM / зеркала** и терминал реальной платы:

```text
litex> mem_read 0x000000B0 16
litex> mem_read 0x000080B0 16
litex> mem_read 0x000100B0 16
litex> mem_read 0x000180B0 16
```

На нашей плате были одинаковые 16 байт. Полный захват и сравнение доказали период `0x8000`. Дополнительно [ROM alias audit](ROM_ALIAS_AUDIT.md). **Не делаем вывод о количестве независимых физических блоков BSRAM.**

## DEMO 4 — Как BIOS проверяет собственную целостность

**HTML → 03 Карта ROM → CRC32**. В ROM по `0x6644` хранятся четыре байта `F6 F4 B1 F2`, то есть little-endian `0xF2B1F4F6`. CRC32 от интервала `[0,0x6644)` совпадает с записанным значением. На плате BIOS ранее сообщал `CRC PASS`. **Это CRC содержимого BIOS, а не CRC FPGA-конфигурации.**

## DEMO 5 — Где и как BIOS подключает UART

**HTML → 05 CSR и UART → «К PC 0x47A4»**. Посмотреть инструкции:

```text
0x47A0: lui   a5, 0xF0003       ; база UART MMIO
0x47A4: lw    a4, 16(a5)        ; uart_ev_pending
0x47A8: sw    a4, 16(a5)        ; acknowledge
0x47B0: sw    a4, 20(a5)        ; uart_ev_enable = 3
0x47B4–0x47BC: чтение/установка CSR 0xBC0 (IRQ_MASK)
```

**Это реконструкция исходного ROM; не пытайтесь исполнять код из этого места как независимую функцию без установленного контекста регистров.** На реальной плате `mem_read 0xF0003014` вернул `03 00 00 00`.

## DEMO 6 — Почему измерительный инструмент меняет результат UART

Через BIOS `mem_read 0xF0003018` трижды наблюдалось `TXEMPTY=0`; исходник LiteX `dump_bytes` сначала печатает заголовок через UART, затем читает регистр. В LAB-20.6 собственный код делает снимок **до своей первой печати** и показал:

```text
TXEMPTY    = 0x00000001
TXEMPTY_AFTER_PRINT = 0x00000000
```

Это **аппаратный опыт** на Tang Nano 20K, не симуляция. Подтверждён эффект самонаблюдения FIFO; не доказано, что всякий `TXEMPTY=0` всегда вызван только диагностикой. [Полный терминальный вывод](../../06-RV32-RAM-Diagnostics/RV32_HARDWARE_EXECUTION_PASS_2026-11-08.md).

## DEMO 7 — BIOS запускает нашу программу RISC-V

**Только реальная плата**, после записи **740 байт** по `0x40010000` и полного readback PASS: `litex> boot 0x40010000`. BIOS выдал `Liftoff!`, затем **уже наша программа** распечатала 11 CPU/MMIO-регистров, значение TXEMPTY после вывода и перешла в `HOLD`. Восстановление заводского терминала — физический RESET. **Не делать `boot` без проверки памяти и не писать во Flash.**

### Для видеодемонстрации

Рекомендуемая логика: (1) открыть HTML и показать запуск, (2) ROM-зеркала, (3) два класса CSR и `uart_init`, (4) физический COM25 с реальной загрузкой, (5) сравнить TXEMPTY до и после печати, (6) продемонстрировать RESET. Чётко подписывать кадры **HTML MODEL** и **REAL FPGA UART**.
