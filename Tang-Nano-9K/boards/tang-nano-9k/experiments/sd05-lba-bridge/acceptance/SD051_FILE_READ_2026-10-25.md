# SD-05.1: read-only FAT32 file access acceptance (25 October 2026)

**Result:** operator-observed hardware FILE READ PASS, with independent byte-content hash verification.

On the same Tang Nano 9K and SD-05 FPGA read-only bitstream, the Python host reader traversed ROOT and the nested system directory to find a regular file at cluster 4. The FAT32 entry reports a **76-byte** file. The operator's PowerShell output shows the copied local file decoded as a brace-delimited Windows volume GUID in UTF-16LE.

Captured PC file SHA-256:
`3115F41CCC5F9B2563517CE88D93D060D715FEE61E0FE77CE00FD4D34BD8E33F`

**Independent check:** encoding the observed 38-character GUID including braces as UTF-16LE (without BOM or line ending) yields exactly **76 bytes**, with precisely the same SHA-256. This establishes the copied file's content and byte length. The full volume GUID is intentionally not reproduced in the public receipt.

Previous hardware checkpoints: SD-05 read-only CMD17 of LBA 0/64/17472; SHA-256 ROOT agreement with SD-04; SD-05.1 successful ROOT and nested-directory listing via COM10.

**Limits:** operator did not provide a separate `SD051_FILE_PASS` console line; evidence consists of the copied file's independently checked content and hash. Multi-sector file reading and multi-cluster FAT-chain traversal remain untested. No SD-card writes, CMD24 or FPGA reprogramming were required.

**Disposition:** SD-05.1 read-only small-file workflow accepted and frozen for this card. Next write tests, if any, belong in a separate experiment on backed-up expendable media.
