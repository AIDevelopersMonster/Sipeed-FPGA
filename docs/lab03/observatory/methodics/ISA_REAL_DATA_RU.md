# Реальные инструкции RISC-V: учебный каталог программы LAB-03

**Назначение:** объяснить исключительно мнемоники, присутствующие в аппаратных T3-трассах LAB-03.3 или в нашем зафиксированном `lab03_boot.hex`. Это **не** каталог всех команд RISC-V. В браузере те же сведения интерактивны во вкладке **03 Команды RV32I**.

## 1. Что именно попало в измеритель

В 12 аппаратных трассах сохранены 269 принятых выборок `FETCH` с **29 различными адресами PC** и **6 различными мнемониками**. Повторы адресов входят в счётчик FETCH, однако не означают 269 завершённых инструкций. Список формируется из реальных машинных слов и декодирования RV32I.

| Мнемоника | Расшифровка | Наблюдаемых FETCH | Разных PC | Фактический пример |
|---|---|---:|---:|---|
| `addi` | Add Immediate | 108 | 13 | `PC 0x048: 0x05400413` → `addi s0, zero, 84` |
| `beq` | Branch if Equal | 87 | 9 | `PC 0x040: 0xFE038CE3` → `beq t2, zero, 0x038` |
| `lw` | Load Word | 39 | 3 | `PC 0x104: 0x0002AF83` → `lw t6, 0(t0)` |
| `jal` | Jump And Link | 12 | 2 | `PC 0x0B4: 0x04C0006F` → `jal zero, 0x100` |
| `sw` | Store Word | 12 | 1 | `PC 0x100: 0x01D2A023` → `sw t4, 0(t0)` |
| `andi` | AND Immediate | 11 | 1 | `PC 0x03C: 0x0013F393` → `andi t2, t2, 1` |

Сумма: 108 + 87 + 39 + 12 + 12 + 11 = **269 FETCH**. Адреса и машинные слова приведены **из настоящей программы и наблюдаемых T3**, а не придуманы для иллюстрации.

## 2. Как читать строку трассы

Наблюдаемая запись в журнале:

```text
FETCH | PC=0x00000100 | WORD=0x01D2A023 | sw t4, 0(t0)
```

- `FETCH` — принятая шиной выборка инструкции из ROM; не архитектурное завершение.
- `PC=0x100` — адрес машинного слова в ROM, кратный четырём байтам.
- `0x01D2A023` — 32-битная кодировка **инструкции** `sw`, а не данные LED.
- `sw` (*Store Word*) — операция записи 32-битного слова по адресу `rs1 + offset`.
- `t4` — регистр источника (ABI-имя для `x29`); `t0` — базовый регистр (`x5`); `0` — смещение в байтах.
- Для нашей программы `t0` устанавливается в `0x20000000` начальной командой `lui`; `t4` содержит программно выбранную маску светодиода. Отдельный захват `LED_WRITE` подтверждает значение **данных** по адресу `0x20000000`.

### Машинное слово и реальные данные — не одно и то же

```text
Инструкция  PC=0x00000100: 0x01D2A023 = sw t4, 0(t0)
Событие MMIO             : 0x20000000 ← 0x00000008 (команда '4')
Событие MMIO             : 0x20000000 ← 0x00000010 (команда '5', отдельный LIVE-опыт)
```

Один и тот же код `sw` может записывать разные значения. UART-команды `4`/`5` — **ASCII-символы, поступающие на устройство**, они не являются мнемониками процессора. `C`, `T`, `?` — команды нашего UART-протокола, а не инструкции ISA.

## 3. Разбор шести наблюдаемых инструкций

### `addi rd, rs1, imm` — Add Immediate, формат I

`rd ← rs1 + sign_extend(imm)` по модулю 2³². Реальная строка: `0x05400413` по `PC=0x048` → `addi s0, zero, 84`. Константа 84 — ASCII-код `T`, с которым программа сравнивает принятый байт. `zero` (`x0`) всегда равен нулю. Другие экземпляры этой же команды в нашем ROM готовят ASCII `C`, `?`, цифры LED.

### `andi rd, rs1, imm` — AND Immediate, формат I

`rd ← rs1 AND sign_extend(imm)`. Реальная строка: `0x0013F393` по `PC=0x03C` → `andi t2, t2, 1`. Берётся бит 0 прочитанного регистра статуса UART; это основа цикла polling.

### `beq rs1, rs2, target` — Branch if Equal, формат B

При равенстве регистров выполняется PC-относительный переход. Реальная строка: `0xFE038CE3` по `PC=0x040` → `beq t2, zero, 0x038`. Если байт UART ещё не поступил, программа возвращается к чтению статуса. Наблюдение FETCH по адресу ветвления **не доказывает**, была ли ветвь принята; у регистратора нет сигнала retirement.

### `lw rd, offset(rs1)` — Load Word, формат I

`rd ← MEM32[rs1 + offset]`. Реальная строка `0x01C2A383` по `PC=0x038` → `lw t2, 28(t0)` читает регистр статуса UART в коде программы. Запрос `0x0002AF83` по `PC=0x104` → `lw t6, 0(t0)` относится к проверке readback маски LED. Наши 12 снимков регистрируют **FETCH этих машинных слов**, но не фактические принятые операции чтения данных.

### `jal rd, target` — Jump And Link, формат J

`PC ← PC + offset`, а `rd ← PC + 4`; если `rd=zero`, адрес возврата отбрасывается. Реальная строка `0x04C0006F` по `PC=0x0B4` → `jal zero, 0x100`. Ведёт к процедуре `apply` для команды OFF; команда `4` идёт по другому месту программы, но приходит к тому же `PC=0x100`.

### `sw rs2, offset(rs1)` — Store Word, формат S

`MEM32[rs1 + offset] ← rs2`. Реальная строка `0x01D2A023` по `PC=0x100` → `sw t4, 0(t0)`. Сам FETCH лишь фиксирует выборку машинного слова; **другое событие** `LED_WRITE` подтверждает принятую запись `0x08` (L4) или `0x00` (OFF) в аппаратных снимках. Сверка этих двух типов событий — центральный момент LAB-03.

## 4. Другие команды **этого** ROM, отсутствующие в наших 12 захватах

Полная активная часть `lab03_boot.hex` содержит **10 мнемоник**: шесть выше и ещё четыре ниже. Они не попали в зафиксированное окно захвата, поэтому неправильно называть их «наблюдённым исполнением».

| Мнемоника | Пример именно из LAB-03 ROM | Назначение в коде |
|---|---|---|
| `lui` (*Load Upper Immediate*, U) | `PC 0x000: 0x200002B7` → `lui t0, 0x20000000` | Задаёт адресную базу регистров MMIO |
| `bne` (*Branch if Not Equal*, B) | `PC 0x108: 0x0BDF9C63` → `bne t6, t4, 0x1C0` | Проверяет несоответствие прочитанной и записанной LED-маски |
| `srli` (*Shift Right Logical Immediate*, I) | `PC 0x2A4: 0x01C55313` → `srli t1, a0, 28` | Выделяет старшую hex-цифру при печати T3 |
| `jalr` (*Jump And Link Register*, I) | `PC 0x2E4: 0x000B8067` → `jalr zero, 0(s7)` | Возвращает управление из процедуры печати |

Оставшиеся **54 слова** из 256 — кодировка `0x00000013`, соответствующая псевдокоманде `nop` (*No Operation*, т. е. `addi zero,zero,0`). Они размещены **после активной программы** как заполнение ROM и не присутствуют среди 269 FETCH. Не следует считать их выполненной работой процессора.

## 5. Имена регистров и форматы

| Термин | Значение |
|---|---|
| `zero` / `x0` | Неизменяемый нуль |
| `ra` / `x1` | Адрес возврата из процедуры |
| `t0` / `x5` | В нашей прошивке — база `0x20000000` |
| `t2` / `x7` | В цикле polling — бит наличия байта |
| `s0` / `x8` | ASCII-константы для сравнения команды |
| `t3` / `x28` | Полученный UART-символ |
| `t4` / `x29` | Маска светодиодов для записи |
| `t6` / `x31` | Буфер обратного чтения LED-регистра |
| `rd` | Регистр назначения |
| `rs1`, `rs2` | Исходные регистры |
| `imm` | Immediate — константа, закодированная в инструкции |
| I / S / B / J / U | Разные расположения полей в 32-битной кодировке RISC-V |
| `opcode` | Младшие семь бит машинного слова, определяющие класс инструкции |

`lw t6, 0(t0)` использует **адресацию base + offset**; `0(t0)` не означает значение нуль, а означает нулевое смещение относительно текущего содержимого `t0`.

## 6. Практические вопросы

1. Найдите в двух RAW-захватах одно и то же `sw t4,0(t0)`. Почему его код не изменился, хотя LED-маска меняется?
2. На каких адресах расположен UART polling? Какие из шести мнемоник его реализуют?
3. Найдите в меню инструкции, присутствующие в ROM, но отсутствующие в 12 аппаратных FETCH. Почему это нормально для ограниченного окна захвата?
4. Укажите различие между `PC=0x104 → lw ...` (зарегистрированный FETCH) и доказанным чтением данных. Какая новая аппаратура понадобилась бы для фиксации DATA_READ?
5. Почему переходы `beq`, `jal`, `jalr` нельзя достоверно считать завершёнными только по факту их появления среди FETCH?

**Вывод:** учебный каталог описывает реально существующие машинные слова, но корректно различает **статический ROM**, **принятую выборку FETCH** и **архитектурное завершение (retirement)**. Его содержимое автоматически обновляется при выборе LIVE-захвата.
