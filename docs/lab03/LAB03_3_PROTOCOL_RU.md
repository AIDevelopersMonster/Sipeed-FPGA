# LAB-03.3 — воспроизводимая кампания аппаратных трасс PicoRV32

**Оборудование:** Sipeed Tang Nano 9K, GW1NR-9C, штатный FT2CH/JTAG, USB-UART COM10 (только на испытанной системе).

**Цель:** получить повторяемый набор аппаратных UART-трасс с известными входными командами, проверить завершающие MMIO-состояния и диагностические флаги, сохранить исходные данные, привязать их к Git-коммиту и SHA256 файла FPGA-конфигурации.

**Что НЕ доказано этим этапом:** эквивалентность инструкции за инструкцией, идентичность времён исполнения, равенство количества FETCH количеству retired instructions, чтение конфигурации из SRAM, отсутствие потерь событий вне окна наблюдения, оптическое состояние LED для каждого запуска.

## Предпосылки

1. Выполнены `SRAM_PROGRAM_PASS` через штатный `programmer_cli.exe` с операцией 2 (SRAM). **Скрипт LAB-03.3 не программирует устройство.**
2. На ПК имеется работоспособный `01-PicoRV32/tools/probe_lab03_2_serial.ps1`, который уже выдал `LAB03_2_TRACE_DECODE_PASS` и `LAB03_2_BOARD_UART_DATA_PASS`.
3. COM10 освобождён. Закройте HTML-вкладки Chrome, использующие Web Serial, и прочие терминалы. USB-кабель не отключать: конфигурация в SRAM энергозависима.
4. Установлены Python 3.9+ и PowerShell 7, доступна команда `pwsh`.
5. Файл `.fs` из той сборки, которая, по протоколу оператора, загружена в плату, сохранён на диске. Его SHA256 — идентификатор локального файла, **не** доказательство фактического содержимого SRAM.

## Запуск из PowerShell 7

```powershell
cd C:\GitHub\Sipeed-FPGA
python .\01-PicoRV32\tests\test_lab03_3_campaign.py
python .\01-PicoRV32\tools\lab03_3_campaign.py run `
    --port COM10 `
    --bitstream .\01-PicoRV32\impl\pnr\picorv32_lab03_nano9k.fs `
    --sequence "4,0,4,0" `
    --rounds 3 `
    --user-code 0x00007D9C
```

Кампания содержит **12 последовательных опытов** (4 команды по 3 цикла); последний опыт — `0`, то есть все LED выключены. За каждым опытом следует освобождение COM-порта штатным скриптом LAB-03.2; текущий инструмент LAB-03.3 не вмешивается в его реализацию.

## Выходные доказательства

Все результаты записываются в `01-PicoRV32/build/lab03_3/campaign_YYYYMMDD_HHMMSS_ffffff/`:

- `manifest.json`: даты UTC, порт, последовательность входных воздействий, версии/хэши скриптов, SHA256 указанной конфигурации, Git commit/branch и состояние рабочего дерева.
- `console/run_XXX_led_N.txt`: исходный консольный ответ **одной** проверки.
- `raw/run_XXX_led_N.txt`: копия UART-дампа, записанного исходным скриптом.
- `runs.json`, `runs.csv`: проверенные статусы, MMIO LED_WRITE, количество FETCH/событий, SHA256 дампа, ошибки.
- `report.md`: итоговая таблица и явные пределы установленных фактов.

Повторная проверка файлов после копирования или передачи архива:

```powershell
python .\01-PicoRV32\tools\lab03_3_campaign.py audit `
    .\01-PicoRV32\build\lab03_3\campaign_YYYYMMDD_HHMMSS_ffffff
```

Заменить суффикс на фактический, указанный программой. При сбое приборный журнал сохраняется, кампания останавливается, общий статус FAIL; повторное программирование FPGA не выполняется.

## Критерии текущего этапа

**CAPTURE_MMIO_PASS:** все запрошенные команды имеют согласованный command echo, объявленные `LAB03_2_*_PASS`, корректные конечные MMIO значения (`0 -> 0`, `N -> 1<<(N-1)`), `done=True`, все флаги потери/конкуренции/продолжающегося захвата равны False, сырые дампы есть и контрольные суммы совпадают.

**TRACE_EQUIVALENCE_PASS пока не присваивается.** Нельзя судить об эквивалентности исполнения по одному числу FETCH. Количество событий при одинаковой команде может изменяться из-за границ наблюдения. Для следующего этапа нужно получить определение записи события (PC, opcode, retire/fetch, timestamp), формат сырых трасс и строго определить одинаковую начальную точку захвата.

## Исследовательская задача: 26/25 против 28/27

Фактические наблюдения 20.10.2026: LED4 в одном захвате имел 26 событий/25 FETCH, в другом 28/27, при одинаковом `LED_WRITE=0x00000008`. Кампания сохранит распределение; отклонение в счётчике FETCH **не считается ни доказанной ошибкой, ни доказанной архитектурной эквивалентностью**. Дальше требуется сравнение содержимого FETCH-событий и известных границ захвата.

### Далее (LAB-03.4)

1. Версионировать формат дампа/версию RTL trace recorder.
2. Извлекать из события PC, opcode, флаги состояния, MMIO и интервал счётчика при наличии.
3. Зафиксировать «якоря» начала/конца трассы: запрос, ответ, метка, состояние автомата захвата.
4. Создать RTL-эталон на той же версии ROM и одинаковых командах, **без подгонки** числа записанных FETCH.
5. Сравнить нормализованные наблюдаемые последовательности и протоколировать первое расхождение. Разделять ISA-инструкции, выдачу на шину памяти и retire: они могут не совпадать по кратности.
6. Повторить серию с 10+ успешными снимками на каждую команду, отдельно измерить долю трасс, не прошедших декодирование.
