# PiKoSoL TP20 / PicoRV32 — GPIO и четыре PMOD на Dock V3714

**Плата:** Sipeed Tang Primer 20K + Dock V3714, FPGA GW2A-18C. **CPU:** PicoRV32 / RV32I. **Связь:** HDMI-текст 96×42, UART 115200 8N1 (COM10 на испытанном ПК). **Дата испытаний:** 21–22 ноября 2026 г.

Это результат практических экспериментов: к исходной системе THLN33 добавлен единый контроллер GPIO для **PMOD1, PMOD2, PMOD3**, сохранён и сделан доступным для чтения прежний **PMOD0 / GPIO**. Программы запускаются как приложения `.bin` из RAM через монитор PiKoSoL. **Заводская Flash не изменяется.**

**Статус подтверждений (не путать):** оператор визуально подтвердил управление настоящими внешними LED×8 на **PMOD0** и **PMOD1**, работу встроенных LED, программы GPIO LIVE, а также команду **ALL LED OFF**. Для **PMOD2 и PMOD3** программная запись и цифровой `OUT/IN` readback работали (`16/16`), но индивидуальное физическое переключение внешних LED на этих двух разъёмах ранее *не было подтверждено*. Общая команда выключения LED подтверждена оператором; сама по себе она не доказывает последовательное управление каждым физическим выходом PMOD2/3. Поэтому здесь зафиксирована поддержка MMIO **всех четырёх PMOD**, но `BOARD PASS` по всем восьми контактам PMOD2/PMOD3 отдельно не заявляется.

## 1. Реестр проверенных программ

Все файлы ниже действительно применялись на плате в данной работе, а не просто были сгенерированы. Для каждого отдельно указан предел подтверждения.

| Программа | Назначение | Аппаратное подтверждение |
|---|---|---|
| [`TP20_GPIO_LED_CHASE.bin`](bin/TP20_GPIO_LED_CHASE.bin) | Последовательное включение 6 встроенных LED, затем OFF | **BOARD PASS** (оператор) |
| [`TP20_GPIO_KEYS_DIP_LED_TERMINAL_5S.bin`](bin/TP20_GPIO_KEYS_DIP_LED_TERMINAL_5S.bin) | Кнопки/DIP → 6 LED, HDMI и события UART (5 с) | **BOARD PASS** для показанных входов/выходов; физическая нумерация кнопок требует исправления |
| [`TP20_PMOD1_SLOW_VISUAL_LATCH.bin`](bin/TP20_PMOD1_SLOW_VISUAL_LATCH.bin) | PMOD1 / LED×8: OFF, ON, `AA`, `55`, рисунок остаётся; следующий `RUN` инвертирует | **BOARD PASS**, реальная внешняя индикация |
| [`TP20_PMOD0_GPIO_SLOW_VISUAL_LATCH.bin`](bin/TP20_PMOD0_GPIO_SLOW_VISUAL_LATCH.bin) | PMOD0 / GPIO: OFF, ON, `55`, `AA`, бегущий огонь 0…7; рисунок остаётся | **BOARD PASS**, реальная внешняя индикация |
| [`TP20_ALL_LED_OFF.bin`](bin/TP20_ALL_LED_OFF.bin) | Выключает 6 встроенных LED, PMOD0; PMOD1/2/3 переводит в Hi-Z | **BOARD PASS**, команда физически подтверждена оператором |

**Не опубликованы как проверенные программы:** `TP20_PMOD23_SLOW_VISUAL_LATCH.bin`, `TP20_PMOD2_PMOD3_LED16_CHASE.bin`, `TP20_GPIO_INPUT_SNAPSHOT.bin`, `TP20_PMOD123_RELEASE.bin`, `TP20_PMOD0_GPIO_ALL_OFF.bin`: у них не было отдельного подтверждения требуемого физического результата. Не делаем GitHub Release и не создаём ветки с кандидатами.

### Как запускать

1. Запрограммировать **рабочую** конфигурацию PiKoSoL GPIO V3714 **в FPGA SRAM**, затем загрузить рабочий `monitor.bin` с XMODEM-CRC. Не записывать заводскую Flash.
2. В File Manager выбрать проверенный `*.bin` и нажать **«Загрузить .bin + RUN»**; COM и скорость должны соответствовать вашей системе.
3. После строки `RUN RETURNED TO PiKoSoL` повторный запуск программы возможен командой `RUN` в Live-терминале, **без повторной передачи BIN**. Для `PMOD0` и `PMOD1` это меняет постоянный рисунок `0x55` ↔ `0xAA`.
4. Если XMODEM завершился ошибкой (`LOAD BAD LENGTH`, неполный ACK, timeout), **не запускать `RUN`** до полного успешного `LOAD`: RAM могла быть частично перезаписана. Нестабильность повторной передачи GPIO LIVE наблюдалась; другие программы продолжали работать. Причина XMODEM пока не доказана.
5. Для безопасного завершения — [`TP20_ALL_LED_OFF.bin`](bin/TP20_ALL_LED_OFF.bin); отключать питание перед перестановкой модулей.

## 2. Пины всех PMOD по фактической `.cst` / патчу V3714

В таблице `bit0`…`bit7` — **индекс бита GPIO в RTL**, справа указан **вывод (ball) FPGA Gowin**, а **не** номер контакта на двухрядном разъёме. Реальный модуль LED×8 нужно подключать по меткам **GND / 3V3** на плате и модуле, а не по направлению таблицы: перевёрнутое подключение опасно.

| Линия | PMOD0 / GPIO | PMOD1 | PMOD2 | PMOD3 |
|---|---|---|---|---|
| GPIO[0] | P9 | J14 | B12 | L9 |
| GPIO[1] | T9 | J16 | C12 | N8 |
| GPIO[2] | T8 | M14 | B13 | N9 |
| GPIO[3] | P8 | M15 | A14 | N7 |
| GPIO[4] | R8 | T12 | B14 | N6 |
| GPIO[5] | T7 | R11 | A15 | D11 |
| GPIO[6] | T6 | T11 | D14 | A11 |
| GPIO[7] | P6 | P11 | E16 | B11 |

* PMOD0, PMOD1 и PMOD2: привязка из исходного `sipeed_tang_primer_20k.cst` THLN33 на зафиксированном коммите (см. «Источники»); PMOD3 — добавленная нашим V3714-патчем привязка, см. [`rtl/apply_gpio_v3714_verified.py`](rtl/apply_gpio_v3714_verified.py).
* Логические I/O — **3,3 В (`LVCMOS33`)**. Питание модуля — 3V3, не 5 В; для LED×8 используются восемь сигнальных линий и контакты GND/3V3.
* Совместное использование физических сигналов: **PMOD0** связан с выводами MIC/WS2812; **PMOD1** — с DVP; **PMOD2/PMOD3** — с трактом RGB LCD. Нельзя одновременно включать конфликтующие периферийные функции или подключать два выходных драйвера на одну линию.
* PMOD1/2/3 в новой системе получают отдельный `DIR`; **PMOD0** сохраняет исходную реализацию и **не имеет `DIR`**.
* Важная особенность V3714: физическая **S4 — RECONFIG**, а не кнопка нашего GPIO-теста. Она может заменить рабочую SRAM-конфигурацию заводской Flash, после чего PiKoSoL потребуется загрузить заново.

## 3. Регистрная карта PicoRV32 / MMIO

Все адреса — **байтовые**, доступ через `volatile uint32_t`. Выходные маски используют младшие 8 бит (встроенные LED — младшие 6 бит).

| Адрес | Имя | Доступ | Смысл |
|---|---|---|---|
| `0x80000000` | `PMOD0_OUT` | R/W | Выходы GPIO0; **инверсия в top-level FPGA** |
| `0x80000004` | `PMOD0_IN` | R | Считывание фактических уровней входных контактных линий PMOD0 |
| `0x80000020` | `PMOD1_OUT` | R/W | Защёлка восьми выходов PMOD1 |
| `0x80000024` | `PMOD1_IN` | R | Синхронизированные уровни восьми контактов |
| `0x80000028` | `PMOD1_DIR` | R/W | Бит `1` — выход, бит `0` — Hi-Z |
| `0x80000030` | `PMOD2_OUT` | R/W | Аналогично PMOD1 |
| `0x80000034` | `PMOD2_IN` | R | Аналогично PMOD1 |
| `0x80000038` | `PMOD2_DIR` | R/W | Аналогично PMOD1 |
| `0x80000040` | `PMOD3_OUT` | R/W | Аналогично PMOD1 |
| `0x80000044` | `PMOD3_IN` | R | Аналогично PMOD1 |
| `0x80000048` | `PMOD3_DIR` | R/W | Аналогично PMOD1 |
| `0x80000050` | `LED_OUT` | R/W | 6 встроенных LED: `1` означает **светится** |
| `0x80000054` | `KEY_IN` | R | Три входных сигнала кнопок (текущие подписи `S2/S3/S5` **не равны достоверной физической нумерации Dock V3714**) |
| `0x80000058` | `DIP_RAW` | R | Сырые уровни SW2–SW5; не интерпретировать без физической проверки полярности |
| `0x8000005C` | `GPIO_ID` | R | `0x47503134` (`GP14`) — идентификатор **нашей** конфигурации |

**Важное ограничение:** `OUT/IN` цифровой readback подтверждает значение выводов или логический путь ввода, **но не гарантирует свечения LED и не заменяет физическую проверку**. Именно это выяснилось на PMOD2/PMOD3.

### Почему на PMOD0 записывают `1`, а на PMOD1–3 `0` для включения LED

На PMOD-модуле светодиод подключён по схеме **active LOW** (светится при низком уровне на его входе). В старом FPGA `top` осталось:

```verilog
assign pmod0 = ~leds_o;  // legacy PORT_OUT (0x80000000)
```

Поэтому `PMOD0_OUT=0x01` даёт на линии 0 **0** и зажигает LED0. Для новых портов прямое управление: `PMOD1_OUT=0xFE` при `PMOD1_DIR=0xFF` даёт LED0=ON, остальные OFF. Нельзя переносить активную полярность PMOD1 на PMOD0 без инверсии.

## 4. Как это сделано в Verilog/SystemVerilog

Фактический модуль контроллера: [`rtl/tp20_gpio_v3714.sv`](rtl/tp20_gpio_v3714.sv), а его подключение к точной версии THLN33 выполняет [`rtl/apply_gpio_v3714_verified.py`](rtl/apply_gpio_v3714_verified.py). Последний меняет `top_board_tp20k.v`, `main_system.sv`, `bus_interconnect.sv`, `.cst`, проект `.gprj` и не переписывает старую логику PMOD0. Используемый синтезируемый фрагмент:

```systemverilog
reg [7:0] out1, out2, out3;
reg [7:0] dir1, dir2, dir3;

genvar i;
generate for (i=0; i<8; i=i+1) begin : gpio_pins
    assign pmod1[i] = dir1[i] ? out1[i] : 1'bz;
    assign pmod2[i] = dir2[i] ? out2[i] : 1'bz;
    assign pmod3[i] = dir3[i] ? out3[i] : 1'bz;
end endgenerate

// Два регистра синхронизации входов в тактовый домен CPU:
reg [7:0] in1meta, in1sync;
always @(posedge clk) begin
    in1meta <= pmod1;
    in1sync <= in1meta;
end
```

Декодер адресов в `bus_interconnect.sv` направляет `0x80000020..0x8000005F` на новый `gpio_inst0`, старый `PMOD0_OUT/IN` остаётся на `0x80000000..0x80000007`. Так сохраняются UART `0x80000008/0C`, таймер `0x80000010...` и HDMI VRAM `0x30000000`.

**Важный порядок включения PMOD1–3:** сначала `DIR=0` (Hi-Z), затем установить `OUT` в безопасное состояние, после чего `DIR=0xFF`. При сбросе контроллера `DIR=0` — внешние линии не должны активно управляться.

## 5. Как управляет портом программа PicoRV32

Пример на **C** — пояснение контракта MMIO, не выдаётся за отдельно скомпилированный или аппаратно испытанный C-бинарник. Полный пример находится в [`examples/gpio_mmio_demo.c`](examples/gpio_mmio_demo.c):

```c
#define REG32(a) (*(volatile unsigned int *)(a))
#define GPIO_ID    0x8000005Cu
#define P0_OUT     0x80000000u
#define P1_OUT     0x80000020u
#define P1_DIR     0x80000028u

void led_sample(void) {
    if (REG32(GPIO_ID) != 0x47503134u) return;
    REG32(P0_OUT) = 0x01u;  // PMOD0: светится LED0
    REG32(P1_DIR) = 0x00u;  // сначала отключить драйверы
    REG32(P1_OUT) = 0xFEu;  // PMOD1: LED0 active LOW
    REG32(P1_DIR) = 0xFFu;  // затем включить восемь выходов
}
```

**Рабочие BIN на самом деле создавались Python-генераторами инструкций RV32I без GCC**. Содержат заголовок `PKD1`: magic `0x31444B50`, длина, entry `0x2000C010`, резервное поле 0. Загрузчик принимает приложение в RAM с `0x2000C000`, ограничение XMODEM-CRC — 12 KiB с padding. Программы защищают GPIO проверкой `GPIO_ID`, выводят статусы через UART DATA `0x8000000C`, рисуют строки непосредственно в VRAM `0x30000000` и **возвращаются в монитор через `jalr x0,0(ra)`**.

**Пример из источника генератора PMOD1:**

```python
P1 = 0x80000020
# x10 — адрес PMOD1; x7 — выходная маска; x15 — старое состояние
c.li(10, P1)
c.emit(sw(0, 10, 8))                   # DIR=0, Hi-Z
c.emit(addi(7, 0, 255), sw(7, 10, 0)) # OUT=0xFF, OFF
c.emit(sw(7, 10, 8))                  # DIR=0xFF, output
# Для последовательного теста: OUT=0xFF,0x00,0xAA,0x55.
# Следующий RUN меняет итоговую защёлку на противоположную.
```

Исходники всех генераторов и офлайн-тестов лежат в [`tools/`](tools/). Их результат после пересборки проверен по SHA256 опубликованных файлов `bin/`. Сборка BIN выполняется на ПК и **не прошивает FPGA**.

## 6. Воспроизведение

**Генерация и проверка BIN (Python 3):**

```powershell
cd .\Tang-Primer-20K\Examples\PR20-03-PiKoSoL-KonSol\GPIO-PMOD-V3714\tools
python -B .\test_gpio_live.py
python -B .\test_pmod_slow.py
python -B .\test_pmod0.py
python -B .\test_all_led_off.py
python -B .\build_gpio_live.py
python -B .\build_pmod_slow.py
python -B .\build_pmod0.py
python -B .\build_all_led_off.py
```

Полученные новые файлы в `tools/` нужно сравнить по SHA256 с проверенными [`bin/`](bin/). **Новые результаты генерации автоматически не получают статус BOARD PASS.** Скрипт `rtl/apply_gpio_v3714_verified.py` предназначен только для *точного* upstream-коммита `d3e24d9176c9361cb583111775f39a9a08cabf52` и прекращает работу, если текстовые якоря не совпадают; это источник модификаций FPGA, а не самостоятельная команда её прошивки. Финальный Gowin build и SRAM-программирование выполняются отдельно по инструкции [SRAM Startup](../SRAM-Startup/README.md).

Проверенная оператором FPGA GPIO `.fs` находится на его Windows-ПК; известная контрольная сумма **SHA256 `7B8B8675EF14D7404E4EF26233BB3BDCE1936449136C56BCFC5497B068421F24`**. **Этого файла в текущем наборе для публикации нет — здесь он не выдаётся за размещённый на GitHub**. Не подменять его старой исходной `.fs` без GPIO GP14.

Публикуются только актуальные подтверждённые BIN и их воспроизводимые источники. Исторические неудачные сборки, логи, кандидатные `.fs`, теги и Releases не создаются.

## 7. Ограничения и следующие испытания

* Физическое соответствие подписей кнопок на Dock V3714 всё ещё не приведено к именам `S2/S3/S5` из исходного контроллера: при тесте пользователь наблюдал смещение и отсутствие отклика одной из кнопок. Не применять эти поля для ответственных функций без корректной ревизии RTL/CST.
* PMOD2/PMOD3 требуют **самостоятельной оптической проверки** каждого физического выхода и при необходимости трассировки общей цепи с RGB LCD; успешный `OUT/IN` не равен LED PASS.
* PMOD0 выводы активны постоянно и не имеют `DIR`; PMOD1–3 после программы LATCH удерживают выходы до `ALL LED OFF` или reset.
* После неудачного XMODEM не исполнять прежний адрес `RUN`, пока полный `LOAD` не подтвердился.
* Не переставлять модули при поданном питании; не путать назначение выводов с Tang Primer **25K** — это другая FPGA и другой `.cst`.
